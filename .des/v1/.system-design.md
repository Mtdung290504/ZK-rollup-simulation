# System Design: ZK-Rollup Simulator (PoC V1)

This document describes the technical architecture, data flow, and state design for the ZK-Rollup simulation, using a **Treasury Symmetric Bridge** to stay compatible with a static ZK circuit.

---

## 1. Architecture Overview

Four independent components communicating over HTTP/JSON:

### L1 Server — Port 3000
Simulates an Ethereum smart contract:
- Locks and releases ETH (Vault)
- Verifies ZK proofs and Merkle proofs
- Stores State Root and DA Root (hashes only)
- Records deposit events and used nullifiers
- Serves the L1 Explorer web UI

### L2 Server — Port 5000
Simulates a Sequencer node:
- Syncs deposit events from L1
- Processes transactions with soft finality
- Manages mempool and transaction list
- Closes batches and triggers ZK proof generation
- Publishes DA blobs to the Archive node
- Serves the L2 Web Wallet UI

### Archive Node — Port 4000
Off-chain data store:
- Receives and stores DA blobs from the Sequencer
- Provides transaction data so users can construct Merkle proofs for withdrawal

## 2. Database Design

State is stored as JSON for easy debugging and inspection.

### 2.1. L1 State — `l1_db.json`

```json
{
  "vault": {
    "0xAliceL1": 50.0
  },
  "bridge_contract": {
    "total_locked_eth": 0.0,
    "current_state_root": "0xINITIAL_STATE_ROOT",
    "batch_history": {
      "1": { "state_root": "0x...", "da_root": "0x..." }
    },
    "pending_deposits": [],
    "claimed_nullifiers": {}
  }
}
```

Fields:
- `total_locked_eth` — ETH currently locked; increases on deposit, decreases on withdrawal
- `current_state_root` — the latest root verified by ZK proof
- `batch_history` — `state_root` and `da_root` per batch, used for withdrawal verification
- `pending_deposits` — deposit events not yet processed by L2
- `claimed_nullifiers` — set of used nullifier hashes to prevent double-spend

### 2.2. L2 State — `l2_db.json`

```json
{
  "accounts": {
    "EDDSA_PUB_TREASURY": {
      "pub_y": "0x...",
      "balance": "340282366920938463463374607431768211455",
      "nonce": "0",
      "index": 0,
      "__user_name__": "Treasury",
      "proven_in_tree": true,
      "snapshot": {
        "balance": "340282366920938463463374607431768211455",
        "nonce": "0"
      }
    }
  },
  "transactions": [],
  "system": {
    "last_proven_tx_index": -1,
    "last_synced_deposit_id": -1,
    "last_proven_deposit_id": -1,
    "merkle_tree": { "nodes": {} }
  }
}
```

Fields:
- `pub_y` — Y coordinate of the EdDSA public key (pub_x is the object key)
- `proven_in_tree` — `true` if this account has appeared in at least one L1-confirmed batch. New accounts from deposits start as `false` until their batch is proven.
- `snapshot` — the `balance/nonce` state at the time of the last successful batch. Used as the starting point when rebuilding the Merkle Tree to ensure it matches `current_state_root` on L1.
- `last_proven_tx_index` — index of the last transaction included in a proven batch
- `last_synced_deposit_id` — last deposit event pulled into the L2 mempool (not yet proven)
- `last_proven_deposit_id` — last deposit event confirmed by L1 after batch approval; used as rollback anchor
- `merkle_tree.nodes` — Sparse Merkle Tree node snapshot after the last batch

**Treasury accounting invariant:**
```
total_locked_eth (L1) = MAX_UINT128 - treasury_balance (L2)
```
When a user deposits 10 ETH: L1 increases `total_locked_eth` by 10; L2 moves 10 from Treasury to the user. Both sides always sum to `MAX_UINT128`.

## 3. Data Flows

### 3.1. Deposit (L1 → L2)

Treasury exists because the ZK circuit has no "mint" operation. All deposits are modeled as `Treasury → User` transfers signed by the Sequencer.

```
1. User calls POST /contract/deposit
   → L1 locks ETH in Vault
   → L1 appends a deposit event to pending_deposits[] with an incrementing deposit_id

2. L2 calls GET /contract/deposits/pending
   → Filters: deposit_id > last_synced_deposit_id
   → For each new deposit:
       a. Create L2 transaction: Treasury → User (amount)
       b. Validate (format, amount > 0)
       c. Apply soft finality:
            Treasury balance -= amount
            User balance    += amount
            Treasury nonce  += 1
       d. Append to transactions[]
       e. Update last_synced_deposit_id

3. On batch close:
   → L2 generates ZK proof
   → L2 publishes DA blob to Archive node
       [L2 → Archive] POST /archive/blobs (batch_id, transactions[])
   → L2 submits batch to L1
       [L2 → L1] POST /contract/batch/submit (proof, state_root, DA_Commitment, num_deposits)
   → L1 checks DA availability (anti data-withholding)
   → L1 verifies proof → updates current_state_root and da_root in batch_history
   → L2 receives success → updates last_proven_deposit_id = last_synced_deposit_id
   → L2 updates each account's snapshot and persists merkle_tree.nodes
```

### 3.2. Transfer (L2 → L2)

```
1. User fetches fee via GET /l2/ui/fee
2. User signs the transaction (EdDSA over Poseidon of 9 fields:
   tx_type=0, from_x, from_y, to_x, to_y, amount, fee, nonce, l1_address=0)
   → Calls POST /l2/transfer (or /l2/ui/sign-and-transfer)

3. L2 validates:
   - EdDSA signature valid
   - (to_x, to_y) is a valid BabyJubJub point
   - fee matches network rate (currently fee = 1)
   - nonce matches sender's current nonce
   - sender_balance >= amount + fee

4. Apply soft finality:
   sender_balance   -= amount + fee
   receiver_balance += amount
   treasury_balance += fee
   sender_nonce     += 1

5. Append to transactions[]

6. On batch close: same as deposit flow (snapshot update + merkle_tree.nodes persist)
```

> **Note:** Because state updates happen before the proof exists (soft finality), the Sequencer must re-validate the full transaction order before generating the proof. A transaction that was valid on arrival may become invalid after earlier transactions changed the state.

### 3.3. Withdrawal (L2 → L1)

L1 cannot see L2 state directly. Withdrawal works by sending funds to Treasury on L2, then claiming on L1 with a Merkle proof from the DA blob.

**Phase 1 — Submit to L2:**
```
1. User enters l1_address (EVM 160-bit hex, 0x-prefixed)
2. User signs: tx_type=2, to=Treasury, amount=X, fee=1, l1_address=<their L1 wallet>
   → POST /l2/transfer
   → Processed as a normal transfer (with extra l1_address format validation)

3. Transaction is included in a batch
   → Batch is proven and submitted to L1
   → DA blob published to Archive
```

**Phase 2 — Claim on L1:**
```
1. User fetches GET /archive/blobs/:batch_id
   → Archive returns transactions[] for that batch

2. User reconstructs the DA leaf:
   Leaf = Poseidon(tx_type, from_x, from_y, to_x, to_y, amount, fee, nonce, l1_address)
   And builds a Merkle proof from the transactions list.

3. User calls POST /contract/withdraw:
   { batch_id, tx_data: {...}, merkle_proof: [...], nullifier_hash: Poseidon(tx_data) }

4. L1 validates in layers:
   a. Batch exists in batch_history
   b. msg.sender == tx_data.l1_address (prevents front-running)
   c. tx_type == 2, to == Treasury, amount > 0 (prevents using transfer proofs to withdraw)
   d. nullifier_hash not in claimed_nullifiers (prevents double-spend)
   e. Merkle proof valid against da_root of that batch_id
   → If all pass: record nullifier, reduce total_locked_eth, send ETH to msg.sender
```

## 4. API Reference

Naming convention:
- `/contract/...` — L1 smart contract (simulated on-chain call)
- `/l2/...` — L2 Sequencer (off-chain)
- `/archive/...` — Archive Node (Data Availability)

### L1 Server (Port 3000)

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/contract/deposit` | Lock ETH in Vault, append deposit event |
| `GET` | `/contract/deposits/pending` | Return unprocessed deposit events |
| `POST` | `/contract/batch/submit` | Receive proof + roots + num_deposits, verify and update state root |
| `POST` | `/contract/withdraw` | Verify Merkle proof, release ETH |
| `GET` | `/contract/state` | Current state (root, locked_eth, batch count) |

### L2 Server (Port 5000)

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/l2/transfer` | Accept transaction, validate 9-field signature, check fee, update state |
| `POST` | `/l2/batch/submit-proof` | Receive proof from CLI tool, relay to L1 + Archive |
| `GET` | `/l2/sync-deposits` | Trigger: sync deposit events from L1 |
| `GET` | `/l2/state` | Current L2 state (accounts, last indexes) |
| `GET` | `/l2/ui/fee` | UI helper: return current network fee |
| `POST` | `/l2/ui/sign-and-transfer` | UI helper: validate curve point, sign, and call /transfer |

### Archive Node

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/archive/blobs` | Sequencer posts DA blob after batch close |
| `GET` | `/archive/blobs/:batch_id` | User/tool fetches transactions[] for a batch |

## 5. Security Invariants

**Dual integrity model:**
- **Deposit integrity = L1 Operations Hash** — governs money entering L2
- **Withdrawal integrity = DA Root (Merkle proof)** — governs money leaving to L1

**L1 Operations Hash (Treasury lockdown):**
The ZK circuit enforces a running hash over all deposit transactions:
1. `from_x` and `from_y` are hardcoded to the Treasury public key
2. The circuit requires `deposit_id` from the L1 event as input
3. Each deposit is hashed into a chain: `newHash = Poseidon(oldHash, deposit_id, to_x, to_y, amount)`
4. This hash is a public circuit output and must match the hash L1 computes from `pending_deposits`

This prevents the Sequencer from minting, reordering, or replaying deposits.

**No Net Mint:** Treasury acts as a finite source. All L2 money comes from Treasury (deposits) and returns to Treasury (withdrawals). Treasury balance decreases by exactly the ETH locked on L1.

**Data Availability:** Every batch transaction is simulated as a blob on L1 (EIP-4844 model). The Archive node represents decentralized blob hosting. Anyone can reconstruct L2 state from on-chain data without trusting the Sequencer.

**Double-spend protection:** L1 stores `claimed_nullifiers`. Each withdrawal nullifier is `Poseidon(tx_data_9_fields)` — unique per transaction, checked before any ETH is released.

**Batch causality:** Transaction `i+1` always executes on the state left by transaction `i`. The Sequencer validates the full order before generating the proof.

**Liveness via padding:** A batch can be closed at any time even with fewer than `N_TXS` real transactions, using `enabled=0` padding slots in the circuit.
